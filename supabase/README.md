# Database and authentication setup

The public preview needs no cloud credentials. Accounts and mutation routes return an explicit 503 until Supabase is configured. A Google login creates an authenticated identity, not a league membership or commissioner role.

1. Create a Supabase project and apply the SQL files in `migrations/` in filename order, using the SQL editor or `supabase db push` after linking the project. This repository does not create or bill for a hosted project automatically.
2. In Google Auth Platform, create a Web application OAuth client. Add the app origin to JavaScript origins and the callback shown on Supabase's Google provider page to Google's redirect URIs (`https://PROJECT.supabase.co/auth/v1/callback`). Configure the client ID and secret in Supabase's Google provider. Keep the secret in that dashboard, not in browser variables or Git.
3. In Supabase Auth URL Configuration, set the production Site URL and add the exact app callback `https://YOUR_APP/auth/callback` to allowed redirects. Add `http://localhost:3000/auth/callback` for local work. Each authorized preview domain needs its own allowed callback.
4. Set `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and `NEXT_PUBLIC_SITE_URL` in local environment/Vercel. These three values are public configuration; Google secrets remain server-side in Supabase. Set `GOOGLE_OAUTH_ENABLED=true` only after the callback configuration is verified. Ordinary league actions use the signed-in user's permissions. The isolated ESPN history service additionally requires the server-only `SUPABASE_SECRET_KEY`, `CRON_SECRET`, `ESPN_S2`, and `ESPN_SWID`; see [history setup](../docs/ESPN_HISTORY_SYNC.md).
5. Import reviewed league records using a trusted migration/import process. Insert snapshot headers with `frozen_at = null`, insert all entries, then set `frozen_at` once. Seed `player_ownerships` from the confirmed bootstrap state. Never replay historical transfers on top of that state. Import historical trades using `application_mode='record_only'`; insert their participants/assets before setting their status to `finalized`.
6. After the commissioner signs in, obtain the verified user UUID in Supabase Auth. A trusted SQL administrator must create the initial `league_memberships` row with role `commissioner`. Assign managers deliberately with `manager_assignments` rows tied to both their auth user and their persistent manager identity. Authenticated clients have no direct table write permission and cannot join themselves, claim a franchise, or promote their role.

For local Supabase, run `supabase start` and `supabase db reset`. Automatic seeding is disabled in `config.toml`; on the resulting empty database, run the checked-in `seed.sql` once followed by `apply-keeper-evidence-review.sql`. That helper applies the original-evidence confirmations from migration 00008 and then the established undrafted rule from migration 00009. The resulting 111 profiles include 100 confirmed and 11 ineligible. Keep the canonical seed's original metadata intact; use migrations for later corrections. Existing databases receive those reviewed confirmations through migrations 00008–00009 without replaying seed data. Google auth is deliberately disabled until real OAuth configuration exists. Configure the two `SUPABASE_AUTH_EXTERNAL_GOOGLE_*` environment variables and enable the provider when ready. Hosted provider settings are managed separately in the dashboard.

## Contracts and invariants

- Teams are stable `franchises`; names, participants, lottery settings, and draft positions are season-specific. Historical manager identities are separate from authenticated users. A manager assignment with an unknown date grants no app access.
- `keeper_profiles.base_round` is the next keeper's underlying cost. `tenure_years` is tenure already accrued, including the fresh draft or first active undrafted season as year one. `keeper_season_records` stores that base separately from the actual payment round. Eligibility must be `confirmed` before submission/review; provisional/unresolved values remain visible only where a genuine evidence conflict or missing fact requires review.
- **10/14/2026 vote passed:** keeper payment costs are incurred only after the keeper deadline has passed and every participating team has submitted, including empty lists. The payment inventory records pick ownership at the deadline; earlier draft saves and submissions neither reserve nor spend picks. Later payment corrections cannot expand a team's keeper budget with picks it did not own at the deadline. Nominal cost progression and tenure remain separate from payment.
- A snapshot is immutable after freezing. Ordinary trade-ledger player transfers update `player_ownerships`; live draft player transfers use the separate `live_draft_roster_ownership` ledger. Both paths preserve the frozen snapshot. Pick transfers update `draft_picks`, retaining the same UUID, year and original franchise through trades and expansion.
- Migration 00017 provisions the reviewed eight-team 2027 draft inventory for cross-year trades: a separate setup season, eight participants, and 104 original-owner picks with real UUIDs. It preserves existing future ownership/status and all current-season state. The private administrative function is idempotent, follows league-first locking, and rejects incomplete repairs after setup. The trade form reads live multi-year inventory separately from the current-year keeper payment pool; display-only reference IDs cannot become trade assets.
- Keeper drafts/revisions, review notes, and approval reservations stay private to the team's actual managers and commissioner. The public sees the finalized selections through `keeper_season_records` after **all** season participants are locked, without private submission notes or user IDs. `participant_count` must match registered teams, avoiding an accidental early reveal during expansion setup.
- Ordinary private-draft revisions invalidate previous approval and cannot edit a locked or revealed submission. The saved player set freezes at the keeper deadline. The separate payment-only action is available for submitted, approved or locked selections to assigned owners/co-managers and commissioners before the live draft starts; it preserves players, submission status, review timestamps, base cost and tenure. After the deadline, replacement picks must be in that team's deadline inventory and still owned and available. Keeper payment validation considers the entire set: an unused eligible pick closer to its base cost prevents overpayment. List order does not matter.
- Migration 00011 permits private draft saves in `setup` and `keeper_selection` before reveal, for assigned managers/co-managers or commissioners only. Selected players must belong to the team's frozen keeper pool and picks must be owned and available. Submission/review/lock still require `keeper_selection`; a save does not open the season, reserve picks or reveal selections.
- Editors retain the revision associated with their loaded selections. A background refresh cannot silently rebase a co-manager's local edits onto another revision. Keeper writes recheck authority after the league lock, including access that expired while the request waited.
- Keeper deadlines and draft dates are nullable, zone-aware schedule settings. The commissioner records schedule changes with a reason and expected revision. The deadline freezes player changes without automatically approving, locking or revealing a submission; the visible countdown itself performs no mutation. Readiness counts are commissioner-only and include teams without submissions; they contain no keeper selections or private review notes.
- Trades do not wait for keeper submissions. Any active league manager can log a trade. Commissioner finalization normally waits for the 24-hour review deadline. An explicit commissioner-only early override requires a reason and is audited; it does not relax other trade protections. Finalization locks the league, verifies every asset and applies all transfers in one transaction. Under the deadline-payment rule, a predeadline keeper preview remains tradable even after approval; transferring that player returns the prior submission for editing. Submitted keeper players freeze at the deadline. Reserved keeper payment picks require a legal replacement allocation committed atomically; picks consumed by live draft selections cannot transfer. Historical `record_only` trades can never execute against current ownership. Voting/automatic veto resolution remains a future workflow.
- Migration 00018 removes the keeper-submission prerequisite from `finalize_trade` while preserving every other authorization, review, ownership, participation and keeper-protection check. The legacy `trading_opened_at` field remains a submission milestone for compatibility and does not determine trade eligibility. Apply `20261008000018_trading_before_keeper_submissions.sql` before deploying the matching trade controls; applying it does not finalize any proposal or change ownership.
- Migration 00019 (`20261008000019_keeper_payment_amendments.sql`) adds audited payment-only changes for owners/co-managers and commissioners, atomic trade/payment replacements, and the explicit commissioner early-review override. It enforces the keeper deadline on player saves, submissions and returns while retaining approval and locking. Apply it before deploying the matching payment and trade controls. The migration itself does not modify keeper selections, pick ownership or trade status.
- Finalized trade assets, historical draft outcomes, rules, frozen snapshots and audit entries are immutable. Keeper payment corrections require an explicit immutable amendment record; the guarded correction changes only payment fields in the current revealed keeper record. Retained players, nominal costs, tenure and rule provenance remain unchanged. Terms/loans are recorded as obligations; future promises do not silently transfer ownership.
- Payment replacements use only picks from that keeper's draft season that the team owned at the deadline, never another team's commitments or a live draft selection. Standalone edits additionally require current ownership and availability; commissioner trade reconciliation additionally requires prospective ownership and availability after all transfers. A later acquisition outside the deadline inventory cannot improve the keeper budget. Every transfer and amendment rolls back on failure. Revealed replacements synchronize assignments, keeper records and used-pick status, then advance draft revision. The public board and roster therefore show each keeper once at the corrected pick. Starting the live draft closes payment changes permanently, including before the first selection.
- Migration 00010 adds the [live draft ledger](../docs/LIVE_DRAFT.md). Only commissioners set order or correct/remove a live selection. Migration 00021 also allows the current pick owner to record a selection while the clock is running. Revision checks, catalog validation and the league lock prevent stale/duplicate selections. Draft corrections cannot edit keeper picks; payment changes use the separate guarded workflow. Draft selections do not update the frozen roster or pre-draft player ownership. Ordinary trade-ledger player transfers pause after keeper reveal; the separate live draft trade action in migration 00023 uses current draft roster ownership. Pick-only transfers retain existing safeguards.
- Migration 00022 applies the **10/14/2026 vote passed** deadline-payment rule to eligible unrevealed seasons. It captures immutable deadline pick ownership before later ownership/status changes. Approval before the deadline or before all submissions reserves nothing; approval or locking after both conditions are met validates and reserves payments from that inventory. Final all-team locking spends the picks and reveals keepers together. New installations run the adoption helper through `apply-keeper-evidence-review.sql` after bootstrap.
- Migration 00023 adds the commissioner-only `execute_live_draft_trade` action used by **Draft Tool → Record draft trade**. It atomically records public trade history, changes live roster ownership, and transfers unspent picks from the current or next draft year. Keeper payment history stays with the original payer. A running clock pauses with its remaining time preserved. Apply migrations 00022 and 00023 before deploying the matching league response and draft-trade controls; anonymous requests cannot execute trades.
- Migration 00024 stores supplied provider ranks privately by authenticated account, season and source. The table has no direct browser grants; its read/save RPCs require active commissioner membership and derive account identity from the session. Rank-bearing BBM imports save only ESPN IDs, supplied ranks and source metadata. Projection statistics remain browser-session data. Newer snapshots replace older ones; stale responses cannot overwrite a newer saved snapshot. The migration and public app bundle contain no paid provider data. Apply it before deploying saved-rank restoration.
- Migration 00012 adds the [draft-slot choice lottery](../docs/DRAFT_LOTTERY.md): verified regular-season standings/current managers, the original Python weighted sampling rule, server-generated unbiased randomness, and one immutable run per season. Each non-playoff team starts with weight 24 and each playoff team with weight 1; selections remove a team and retain the remaining weights. Inputs are public according to league visibility; saved priority and per-draw entropy remain commissioner-only. Retry returns the original result. The draw never changes public choice order, draft slots, phase, keeper reveal or ownership.
- Migration 00013 adds explicitly shared replay snapshots. A commissioner creates one unguessable link per saved run; anyone with that link can read only the dates, year and eight ordered manager/team labels. Direct browser table access is denied. The original draw/audit stays private, sharing never assigns slots, and deleting a source run invalidates its shared replay.

- Migration 00014 adds commissioner-only withdrawal of pending live proposals with a required reason and immutable audit entry. Withdrawn records and their original legs remain readable under the existing participant/commissioner permissions. Finalized, historical and archived-season trades cannot be withdrawn. A corrected proposal links the withdrawn original and starts a fresh 24-hour review; this adds no voting or veto policy. Apply `20261003000014_trade_withdrawal.sql` before deploying the updated trade API.

## HTTP routes

Migration `20261008000021_live_draft_clock.sql` adds the 90-second default draft clock, commissioner start/pause/resume/configuration, owner picks and private team queues. Apply it before deploying the matching app. Existing drafts with selections migrate paused; installation never starts a draft. The migration attempts to enable `pg_cron` and registers `live-draft-clock` to run `select private.tick_live_drafts()` every second. Verify that job is present and active in Supabase Cron before draft day. If the extension is unavailable or setup emits a warning, enable Supabase Cron and register that same one-second SQL job. Connected browsers also request expiration ticks, but automatic picks without an open board require the scheduled job. The job runs with the migration administrator's database role and uses no browser credentials.

- `GET /api/draft-queue?seasonId=UUID&franchiseId=UUID`: private queue for an actively assigned owner/co-manager. Commissioner status alone grants no queue access.
- `POST /api/draft-queue`: `{ seasonId, franchiseId, expectedRevision, playerIds }`, with at most 100 unique verified available players. Queue revisions are independent of the draft board. Both routes return `{ queue: { seasonId, franchiseId, revision, playerIds } }`.

- `GET /auth/login?next=%2F%3Fview%3Dmy-team`: Google OAuth; `GET /auth/callback`: PKCE exchange with local-only next path; `POST /auth/signout`: local session sign-out.
- `GET /api/session`: authenticated user plus real league memberships and manager assignments. No fabricated account is returned when unconfigured.
- `GET /api/draft-projection-ranks?seasonId=UUID`: the active commissioner's own BBM rank snapshot or `null`, never another account's list. Returns private, noncacheable responses. The snapshot can populate player rank/value columns without supplying team forecasts.
- `POST /api/draft-projections`: commissioner-only ESPN/Yahoo refresh or CSV/TSV import. A rank-bearing BBM import additionally saves its rank-only snapshot through the account-scoped RPC; a save failure leaves imported statistics usable and reports that persistence needs a retry. Legacy rankless ESPN/Yahoo browser imports receive one automatic rank-refresh attempt, retaining manual retry controls.
- `GET /api/league`: anonymous Supabase overlay for the current draft year; returns `data` in the public `LeagueData` format, `seasonId`, `phase`, `franchiseIds` (numeric UI team ID to permanent UUID), `usedPickIds`, `draftOrder`, and `revealedKeepers`. Live ownership, costs, tenure, review status, and picks fully replace the preview snapshot. Historical draft/charter material and imported manager labels remain reference metadata. A failed live query returns 503, never a silently stale preview.
- `POST /api/season`: commissioner opens selections with `{ action: "open_keeper_selection", seasonId, note }` after verifying participant count, the frozen roster and ownership, keeper profiles, and a complete valid pick inventory. The note records the setup review; unresolved profiles still cannot be submitted until reviewed.
- `GET /api/season?seasonId=UUID`: commissioner-only overview of all participating franchises, submission states, manager-access counts, profile verification counts, schedule and inventory completeness. Actual pick holdings may differ from the original allocation after trades.
- `POST /api/season`: `{ action: "update_schedule", seasonId, expectedRevision, keeperDeadline, draftAt, seasonTimeZone, note }`. Dates are ISO timestamps with offsets or `null`; the display timezone is an IANA name such as `America/New_York`. A conflicting revision requires explicit reload.
- `GET /api/keepers?seasonId=UUID`: current submissions permitted by database row-level security.
- `POST /api/keepers`: `{ action: "save", seasonId, franchiseId, expectedRevision: 0, assignments: [{ playerId: 123, pickId: "UUID" }] }`; later saves pass the current revision. Empty selections are valid.
- `POST /api/keepers`: `{ action: "submit" | "approve" | "reject" | "lock", submissionId, expectedRevision, note? }`. Rejection requires a reason; review and lock require commissioner membership.
- `POST /api/keepers`: `{ action: "reassign_payments", submissionId, expectedRevision, assignments: [{ playerId: 123, pickId: "UUID" }], note }`. Assigned owners/co-managers or commissioners may replace payments for the same saved player set before the live draft starts. The reason is required, revision conflicts require reload, and status/cost/tenure remain unchanged.
- `POST /api/trades`: any active league manager logs `{ seasonId, category: "player_only" | "advanced", terms, players: [{playerId,fromFranchiseId,toFranchiseId}], picks: [{pickId,fromFranchiseId,toFranchiseId}], obligations: [{kind,terms,fromFranchiseId,toFranchiseId,dueAt?}] }`. Returns `tradeId` without transferring anything.
- `POST /api/trades/withdraw`: commissioner-only `{ tradeId, reason }`, with 5–2,000 trimmed characters. Retains the proposal, reason, time and audit trail without transferring ownership.
- `POST /api/trades`: commissioners may additionally include `correctsTradeId` referencing a withdrawn live proposal in the same season. A revision is a separate proposal with its own complete review period.
- `POST /api/trades/finalize`: `{ tradeId, keeperPayments?: [{ submissionId, expectedRevision, assignments: [{ playerId: 123, pickId: "UUID" }] }], note?, overrideReview? }`, commissioner-only. The default action waits for review. `overrideReview: true` explicitly permits early finalization with a required reason. Supplied payment allocations require a reason and are applied with all trade legs in one transaction after prospective ownership validation; omitting them preserves the standard path.
- `POST /api/keeper-profiles`: commissioner review `{ seasonId, playerId, baseRound: number | null, tenureYears: number | null, verification: "confirmed" | "provisional" | "unresolved" | "ineligible", note }`. An approved selection must be rejected before changing its profile. Review creates an audit event.
- `GET /api/draft-board?seasonId=UUID`: allowlisted public board, hiding unrevealed players and unassigned order. `POST /api/draft-board`: `set_order`, `record`, `correct`, `undo`, `configure`, `start`, `pause`, or `resume`, all with `seasonId` and `expectedRevision`; order/correction/removal require a note. All require commissioner access except `record`, also allowed for the assigned current pick owner. Public `{ action: "tick", seasonId }` can only process an expired server deadline. See [the action schema](../src/lib/draft-board.ts) and [draft walkthrough](../docs/LIVE_DRAFT.md).
- `GET /api/draft-lottery?seasonId=UUID`: verified standings, odds, source code and run status; only commissioners receive the saved result. `POST /api/draft-lottery`: `{ action: "generate", seasonId }`, authenticated commissioner only. No client-controlled seed or order. Duplicate calls recover the original immutable run.
- `POST /api/draft-lottery/share`: `{ seasonId }`, authenticated commissioner only; publishes the allowlisted replay and returns the same link on retries. `GET /api/draft-lottery/share?shareId=UUID`: public read by unguessable token, with no private draw details or link enumeration.
- `POST /api/trades/obligations`: commissioner resolution `{ obligationId, status: "fulfilled" | "waived", note }`. Settlement is recorded; an obligation does not automatically execute a second asset transfer.

Older draft rows can preserve `was_keeper = null`. Historical players whose ESPN identity has not been resolved remain in import staging; do not fabricate player IDs or treat unknown keeper status as false.

Mutation routes require same-origin requests, strict JSON validation, and database authorization. All user-directed changes require a server-verified session; the expiration-only draft tick is public and never accepts a player or timestamp. API/auth responses are not shared-cacheable. Before production launch, run database tests and verify Google callback, manager provisioning, and RLS against the actual hosted project.
